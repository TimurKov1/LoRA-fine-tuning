# Дообучение LLM для извлечения данных из объявлений об аренде квартир

Небольшие модели Qwen2.5 (0.5B и 1.5B) дообучены с помощью LoRA и QLoRA превращать текст объявления о сдаче квартиры в строгий JSON из девяти полей. Проект проходит весь путь: схема и данные, baseline, обучение с нуля написанным циклом, оценка на синтетических и реальных текстах, разбор ошибок, экспорт в GGUF и запуск через Ollama.

Пример (1.5B QLoRA, GGUF Q8_0 в Ollama):

```
Сдам 2к квартиру, 54 кв.м, 5/9 этаж, м. Сокольники, 65 тыс. в месяц. Без животных. Звонить +7 916 123-45-67, Ирина
```
```json
{"rooms": 2, "area_m2": 54.0, "floor": 5, "total_floors": 9, "metro": "Сокольники", "price_rub": 65000, "pets_allowed": false, "phone": "79161234567", "contact_name": "Ирина"}
```

## Задача и схема

Из текста нужно получить ровно такой набор ключей (все обязательны, лишние запрещены; если данных в тексте нет, значение `null`):

| Поле | Тип | Правило |
|---|---|---|
| `rooms` | int | число комнат, студия = 0 |
| `area_m2` | float | общая площадь, м² |
| `floor`, `total_floors` | int | этаж и этажность дома (этаж не больше этажности) |
| `metro` | str | название станции без «м.» и «метро» |
| `price_rub` | int | аренда в месяц, без залога и коммунальных платежей |
| `pets_allowed` | bool | `true` разрешены, `false` запрещены, `null` не сказано или «по договорённости» |
| `phone` | str | 11 цифр, начинается с 7 (нормализуется валидатором) |
| `contact_name` | str | только имя (ник в мессенджере именем не считается) |

Схема описана на pydantic (`schema.py`) и служит сразу тремя целями: проверкой ответа модели, проверкой обучающих данных и сравнением с эталоном.

## Данные

| Набор | Размер | Происхождение |
|---|---|---|
| `train` | 2000 | синтетика |
| `val` | 200 | синтетика |
| `test` (`synth_test`) | 100 | синтетика |
| `real_1` | 31 | реальные объявления с сайта, блок «Станция (расстояние)» + описание |
| `real_2` | 30 | реальные объявления из Telegram, свободный текст |

**Синтетика.** Сначала случайно собирается эталонная запись, потом по ней строится текст из словарей и шаблонов, так что метки точны по построению. Тексты разной длины (короткие, средние, длинные с абзацами, «ключ: значение»), с разными записями чисел (`45к`, `45 тыс.`, `49.000 р.`), склонёнными названиями станций и именами, опечатками, капсом и числовыми ловушками (площадь кухни, залог, коммунальные платежи, год дома). Генератор в репозиторий не входит.

**Реальные наборы** (`data/rent_msk_test.jsonl`, `data/rent_msk_test_v2_diverse.jsonl`) собраны вручную из открытых объявлений. Телефоны, имена, ники в мессенджерах и почта заменены на вымышленные, ссылки на оригиналы удалены; адреса (улица и дом) оставлены, потому что это часть того, что модель разбирает. Эталоны приведены к правилам схемы (студия = 0, каноническое название станции, имя без отчества), независимой проверки вторым человеком у них не было.

Важная оговорка: словарь синтетических данных конечен (около 2100 слов), и тест из того же генератора почти не содержит незнакомых слов (меньше 1%). Поэтому синтетический тест показывает, как хорошо модель освоила задачу на привычном языке, а не как она справится с чужими текстами. Для этого и нужны реальные наборы.

## Метод

- **Модели:** `Qwen2.5-0.5B-Instruct` (LoRA, fp32) и `Qwen2.5-1.5B-Instruct` (QLoRA: 4-бит NF4, двойная квантизация, вычисления в fp16).
- **LoRA:** `r=16`, `alpha=32`, `dropout=0.05`. Сравниваются два набора слоёв: только внимание (`q,k,v,o`) и внимание + MLP (`+ gate, up, down`).
- **Обучение:** собственный цикл (`training.py`), AdamW, `lr=2e-4`, линейный разогрев 10 шагов и линейное затухание, 2 эпохи, микробатч 4 с накоплением 4 (эффективный батч 16), `seed=0`. На 0.5B около 6 секунд на обновление на T4.
- **Loss только по токенам ответа.** Метки промпта и заполнителей равны `-100`; логиты считаются только для хвоста последовательности (`logits_to_keep`): при словаре в 152 тысячи токенов логиты по всем позициям занимают гигабайты. Вместе с `gradient checkpointing` это позволило обучать на Mac M1 с 16 ГБ: микробатч из самых длинных примеров вместо нехватки памяти (более 19 ГиБ) занимал 6.9 ГБ.
- **Промпт короткий и постоянный** («Извлеки данные из объявления о сдаче квартиры в JSON. Объявление: ...»): схему и правила модель усваивает в весах, длинная инструкция не нужна. Используется стандартное системное сообщение Qwen, оно было в каждом обучающем примере.
- **Метрики** (`evaluation.py`), схема строгая (`extra="forbid"`, все ключи обязательны):
  - `valid_rate`: ответ разобрался как JSON и прошёл схему;
  - `exact_match`: все 9 полей совпали с эталоном (доля от всех ответов);
  - `field_acc`: доля верных полей из всех возможных (невалидный ответ даёт ноль).

## Результаты

### Baseline

Необученная `Qwen2.5-0.5B-Instruct` с длинным промптом (список полей, правила, пример), синтетический тест: `valid 0.62`, `exact 0.08`, `field_acc 0.45`; во всех ответах markdown-обёртка. С коротким промптом базовая модель не знает схемы и придумывает свою: вложенные объекты, лишние ключи, выдуманные координаты и почта.

### Дообученные модели

Val loss после 2 эпох: 0.5B только внимание **0.0124**, 0.5B внимание + MLP **0.0044**, 1.5B QLoRA **0.0015** (во всех случаях между train и val нет заметного разрыва).

| Модель | Тест | valid | exact | fields |
|---|---|---|---|---|
| 0.5B, внимание | синтетический (100) | 1.00 | 0.84 | 0.98 |
| 0.5B, внимание + MLP | синтетический (100) | 0.99 | 0.97 | 0.99 |
| **1.5B QLoRA** | синтетический (100) | 1.00 | **0.98** | 1.00 |
| 0.5B, внимание | реальный `real_1` (31) | 1.00 | 0.19 | 0.87 |
| 0.5B, внимание + MLP | реальный `real_1` (31) | 1.00 | 0.26 | 0.89 |
| **1.5B QLoRA** | реальный `real_1` (31) | 1.00 | **0.32** | 0.91 |
| 0.5B, внимание | реальный `real_2` (30) | 0.97 | 0.13 | 0.82 |
| 0.5B, внимание + MLP | реальный `real_2` (30) | 0.97 | 0.20 | 0.84 |
| **1.5B QLoRA** | реальный `real_2` (30) | 1.00 | **0.33** | 0.89 |

Выводы:

- Дообучение решило задачу формата: ответ всегда валидный JSON без обёртки, лишних ключей и пропущенных полей, а длинная инструкция стала не нужна.
- **Адаптеры в слоях MLP важны:** при тех же данных `exact` на синтетике вырос с 0.84 до 0.97. Внимание решает, на что смотреть, MLP преобразует «60 т.р.» в 60000, нормализует телефон, выбирает между `null` и `0`.
- **Размер модели помогает на реальных текстах:** 1.5B лучше обеих 0.5B на обоих реальных наборах, при том что на синтетике разница между ними почти исчезает (тест насыщен).
- **Разрыв между синтетикой и реальностью большой:** 0.98 против 0.32–0.33 по `exact`. Это главный результат оценки и главное ограничение проекта.

### Что ошибается на реальных текстах

Разбор ошибок показал, что в основном это пробелы в обучающих данных, а не неспособность модели:

| Причина | Пример |
|---|---|
| **Метро: несколько станций** в блоке «Станция (расстояние)»; в эталоне ближайшая, модель берёт соседнюю или `null` | Алтуфьево / Лианозово |
| **Станции, которых не было в обучающем списке** | Новохохловская, Локомотив, ЗИЛ, Красногорская |
| **Район, улица или шоссе вместо станции** | «район Хамовники», «Бурковский проезд» |
| **Telegram-ник вместо имени** (1.5B возвращает `user1010`), у 0.5B выдуманные имена | эталон `null` |
| **Выдуманный телефон** `79876543210`, когда в тексте только ник | 1.5B, три случая |
| **Цена вместе с залогом** | «50000 + 40000 залог» → 90000 |

Если при оценке считать верной любую станцию, названную в тексте, а ник вместо имени заменять на `null` (смягчённые правила, пересчёт постфактум), метрики 1.5B на реальных наборах становятся такими: `real_1` exact 0.32 → **0.48**, fields 0.91 → 0.94; `real_2` exact 0.33 → **0.63**, fields 0.89 → 0.94. Эти цифры показывают потолок при пересмотре правил разметки, а не улучшение модели; основными считаются строгие.

### Проверка забывания

На обычных вопросах без нашего промпта модель с адаптером отвечает текстом, а не JSON; ответы стали короче и суше (адаптер учился на коротких ответах). Базовая 0.5B сама слаба в русском и арифметике, поэтому заметной деградации из-за адаптера выделить не удалось. Проверка качественная (6 вопросов).

### Экспорт в GGUF и запуск в Ollama

Адаптер QLoRA 1.5B слит с базой, сконвертирован в GGUF (F16) и квантизован. Реальные наборы вместе (61 объявление), температура 0:

| Вариант | Размер | valid | exact | fields | Совпадает с исходной моделью |
|---|---|---|---|---|---|
| исходная (адаптер на 4-битной базе, PyTorch) | | 1.00 | 0.33 | 0.903 | |
| слитая, PyTorch fp32 | 5.8 ГБ | 0.95 | 0.36 | 0.867 | 67% |
| GGUF F16 | 3.09 ГБ | 0.93 | 0.34 | 0.856 | 64% |
| **GGUF Q8_0** | **1.65 ГБ** | 0.93 | 0.34 | 0.856 | 62% |
| GGUF Q4_K_M | 0.99 ГБ | 0.93 | 0.34 | 0.852 | 59% |

На синтетическом тесте все три GGUF совпадают с исходной моделью в 96–97% ответов, `exact` 0.95–0.97. Скорость в Ollama на Mac M1: около 5 секунд на пример у F16 и Q8_0, около 4 у Q4_K_M (ответ порядка 90 токенов).

**Что показала проверка.** Конвертация и квантизация почти ничего не теряют: F16, Q8_0 и Q4_K_M дают практически одинаковые метрики, а слитая модель в обычном PyTorch ведёт себя так же, как F16 в Ollama. Отличие от исходной возникает при слиянии: QLoRA-адаптер обучался на 4-битной базе, а сливается с базой в полной точности, то есть поправки подстроены под ошибки округления базы NF4. На привычных текстах этого не видно, на реальных `valid` падает с 1.00 до 0.93–0.95 (иногда появляется список станций вместо строки). Чтобы получить точную копию обученной модели, нужно перед слиянием развернуть 4-битную базу в fp16 (`dequantize()`, требуется CUDA), в проекте это не сделано.

Рекомендуемый вариант для запуска: **Q8_0**, компактный: Q4_K_M.

## Ограничения

- Реальные наборы маленькие (31 и 30 объявлений): один пример меняет `exact_match` на 3 пункта.
- Эталоны реальных наборов не проверялись вторым человеком; часть правил (выбор станции, ник как имя) принята по ходу разбора.
- Синтетический тест насыщен и не различает модели; судить о качестве нужно по реальным наборам.
- Один запуск на конфигурацию, повторов с другими `seed` нет.
- Слитая GGUF-модель немного отличается от обученной (см. выше).

## Структура проекта

```
config.py            имя модели, токенизатор, устройство, путь к llama.cpp
schema.py            схема Listing (pydantic): типы, ограничения, нормализация телефона
data_utils.py        промпт, кодирование примера с маской меток, батч с заполнителями, загрузчики
models.py            make_model (LoRA), make_qlora_model (QLoRA), загрузка готовых адаптеров
training.py          функция потерь по токенам ответа, val loss, цикл обучения
inference.py         generate_json, очистка markdown, обычный чат
evaluation.py        прогон по тесту, метрики, разбор ошибок, сохранение результатов
deploy.py            слияние адаптера, GGUF, квантизация, Ollama
run.ipynb            все эксперименты одним ноутбуком (только вызовы)
experiments/         ранние эксперименты и baseline с длинным промптом
data/                синтетические наборы (train, val, test)
models/              обученные адаптеры (LoRA 0.5B ×2, QLoRA 1.5B)
results/             ответы моделей на тестах (по файлу на модель и тест)
```

## Запуск

Нужен Python 3.12 или новее.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Дальше откройте `run.ipynb` из корня проекта. Разделы 0–1 готовят данные, 2 обучает (пропустите, если адаптеры уже есть в `models/`), 3–7 оценивают и разбирают результаты, 8 экспортирует в GGUF.

- Обучение и оценка LoRA работают на Mac (`mps`), на CPU и на NVIDIA GPU. QLoRA обучается только на NVIDIA GPU (нужен `bitsandbytes`).
- Для раздела 8 нужны Ollama и `llama.cpp` в `~/llama.cpp` с собранной утилитой `llama-quantize` (путь задан в `config.py`).

## Что можно улучшить

- Дополнить генератор данных по найденным ошибкам: блок «Станция (расстояние)», полный список станций (МЦК, МЦД, новые), контакты через ник без телефона, район и улица вместо метро, цена рядом с залогом.
- Слить QLoRA-адаптер с развёрнутой 4-битной базой и перемерить GGUF.
- Расширить реальные наборы и проверить эталоны вторым человеком.
- Попробовать обучение по награде, которую считает программа (валидность схемы, число верных полей).
